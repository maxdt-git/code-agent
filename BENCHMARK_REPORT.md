# Benchmark Report

Every number in this report comes from a `solution.json` in
[`benchmark/`](benchmark/), validated by the moulinette (`moulinette_eval
validate swebench`, result saved next to each file as `.validation.txt`).
The tables are generated by [`scripts/bench_report.py`](scripts/bench_report.py)
and the runs are launched by [`scripts/bench.sh`](scripts/bench.sh).

Runs were made on 2026-10-26, 2026-10-27 and 2026-10-28: the free-tier
daily quotas (section 3) did not allow all of them on the same day.

## 1. Setup

### Agent version

- Agent: the SWE-bench agent of this repository (`python -m agent_swebench`),
  25 iterations at most, 840 s deadline, 300,000 / 10,000 token budget.
- Every benchmark run uses `--no-fallback`: the client does not switch to
  another model, so each run measures one model only. It changes nothing
  else in the agent.
- Version **v1** for the model comparison. Version **v2** (section 5) only
  changes what the `run_tests` tool returns.

### Models and providers

All on free tiers, keys loaded from `.env`.

| Model | Provider | Why it was selected |
|---|---|---|
| `gemini-3.5-flash-lite` | Google AI Studio | accepts long requests, default model of the agent |
| `gemini-3.6-flash` | Google AI Studio | fastest Gemini model on a 10,000-token request (5.3 s) |
| `qwen/qwen3.8-27b` | Groq | fastest provider (about 0.5 s per request), best MBPP model |
| `openai/gpt-oss-120b` | Groq | largest model available on Groq |
| `cohere/north-mini-code:free` | OpenRouter | fastest OpenRouter free model on a 10,000-token request (1.9 s), code model |

### Tasks

`sympy__sympy-13480`, `pydata__xarray-4629` and `sympy__sympy-14711`: the
three tasks the subject suggests to start with. They cover two
repositories, and they range from a one-word typo (13480) to a change in an
operator of a class (14711). All three belong to the exam pool of
`exam_swebench.sh`, so they also measure exam readiness.

`qwen/qwen3.8-27b` was also run on the other three exam-pool tasks
(`sympy__sympy-18189`, `django__django-11066`,
`scikit-learn__scikit-learn-13439`).

per-minute limits: the client waits and retries, and the run goes on.

### Free-tier limits that decide what each provider can do

| Provider | Limit | Effect on SWE-bench |
|---|---|---|
| Groq (`qwen3.8-27b`, `gpt-oss-120b`) | 8,000 tokens per minute (header `x-ratelimit-limit-tokens`), 200,000 tokens per day | one request cannot exceed 8,000 tokens; about 5 tasks per day per model |
| Gemini | 20 requests per day per model and per project (`GenerateRequestsPerDayPerProjectPerModel-FreeTier`) | `gemini-3.6-flash`: 1 or 2 tasks per day |
| OpenRouter | 50 free-model requests per day per account (`X-RateLimit-Limit: 50`) | 2 tasks per day, shared by all OpenRouter models |

### Availability over time

- Model names change: `llama-3.1-8b-instant` (Groq) and `gemini-2.5-flash`,
  `gemini-2.5-pro` (Gemini) answered HTTP 404 in October 2026.
- Latency of one model varies a lot from day to day:
  `gemini-3.5-flash-lite` averaged 19.7 s per request on 2026-10-26 and
  8.5 s on 2026-10-27 for the same tasks.
- Several OpenRouter free models were saturated (HTTP 429) or reserved to
  paying accounts (HTTP 403) when probed on 2026-10-23.

### Fallback in practice

Before `--no-fallback` existed, three `qwen/qwen3.8-27b` runs hit a Groq
limit and the client switched to `cohere/north-mini-code:free` on its own
(files `*__qwen-then-north-mini-code__run1.json`). Two of them still passed,
and `xarray-4629` passed **without** any `final_answer`: the agent always
takes the patch from the container at the end, so work done before the
model stopped is kept.

## 5. Ablation study

### Change

In v1, `run_tests` returned the last 10,000 characters of stdout + stderr.
The SWE-bench evaluation script prints the test results on stdout, then a
long `set -x` trace and warnings on stderr (356,144 characters in total for
`sympy-13480`). The tail kept only the trace: **the model never saw whether
its tests passed.**

In v2 (`TEST_OUTPUT=section`), `run_tests` merges both streams and returns
only the part between the `>>>>> Start Test Output` and
`>>>>> End Test Output` markers of the script, without the trace lines
(3,558 characters for `sympy-13480`, ending with
`tests finished: 44 passed, 1 exceptions`).

### Result

Same model (`gemini-3.5-flash-lite`), same three tasks, `--no-fallback`:

| Task | Version | Pass | Iterations | Input tokens | First visible passing `run_tests` | `final_answer` |
|---|---|---|---|---|---|---|
| sympy-13480 | v1 | PASS | 9 | 21,855 | never | 9 |
| sympy-13480 | v2 | PASS | 12 | 26,187 | 11 | 12 |
| xarray-4629 | v1 | PASS | 9 | 41,424 | never | 9 |
| xarray-4629 | v2 | PASS | 9 | 28,639 | not called | 9 |
| sympy-14711 | v1 | PASS | 25 | 155,923 | never | 25 |
| sympy-14711 | v2 | PASS | 20 | 91,285 | 18 | 20 |
| **Total** | v1 | 3/3 | 43 | 219,202 | | |
| **Total** | v2 | 3/3 | 41 | 146,111 | | |

- Input tokens over the three tasks: **−33 %** (219,202 → 146,111).
- On the longest task, 5 fewer iterations and −41 % input tokens: the model
  saw the tests pass at step 18 and submitted 2 steps later, instead of
  using the whole budget.
- On `sympy-13480`, v2 costs 3 more iterations: the model now runs the
  tests before submitting, which it had no reason to do in v1.
- Submission discipline (iterations between the first visible passing
  `run_tests` and `final_answer`): 1 on `sympy-13480`, 2 on `sympy-14711`.
- Limits: one run per task and version, so the differences include the
  model's randomness. The time per task dropped by half too, but this comes
  from the provider (section 3), not from the change.

## 6. Conclusions

**Selected models**

- **SWE-bench: `gemini-3.5-flash-lite`** (Gemini) as the default model: 3/3
  on the common tasks in both agent versions, no retry, no provider error,
  and a daily quota large enough for several tasks. Its weak point is
  latency (8 to 20 s per request), which is safe within the 900 s limit.
- **`qwen/qwen3.8-27b`** (Groq) as the second choice: the best pass rate,
  **6/6 on the whole exam pool**, about 40 times faster per request. But
  two of its runs were cut by the 8,000-token request size limit (they
  passed only because the agent keeps the patch made so far), and its
  200,000-token daily quota covers about five tasks: on a harder task, it
  is the provider, not the model, that would fail.
- **MBPP: `qwen/qwen3.8-27b`** on Groq: 19/20, 1.95 iterations and about
  1,400 input tokens per task (23 % of the limit), 0.5 s per request.

**Models that can be disregarded for this agent**

- **`cohere/north-mini-code:free`**: it never answers in the agent's format
  (0 executed steps in 75, over three tasks), so it cannot be used without
  supporting its own tool-call format in the extraction layer.
- **`openai/gpt-oss-120b` on Groq**: it calls its built-in tools, which
  Groq rejects, and its requests hit the 8,000-token limit.
- **`gemini-3.6-flash`**: fast (3.2 s per request) and 2/3, but its daily
  quota covers about one task per day, and it spent 22 steps on
  `sympy-14711` without editing the file.

**What the data says about the agent**

- Making the test results visible (v2) reduced input tokens by 33 % without
  losing a task: v2 becomes the default.
- The free tiers, not the models, are the main risk: 5 of the 6 provider
  errors of section 3 are daily quotas or request size limits.
- The agent generalises beyond the three tasks used to build it: with
  `qwen/qwen3.8-27b`, it solves the three other exam-pool tasks, including
  two repositories (django, scikit-learn) it was never tried on.
